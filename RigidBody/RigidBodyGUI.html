Tutorial: Rigid Body Refinement

Contributors: Kristian Lytje, Jan Skov Pedersen, Andreas Haahr Larsen, Jeppe Breum Jacobsen.


SAXS data on the PA2 protein in solution with a fitted hydration layer.

Before you start

  • For an introduction to analysis of SAXS data on proteins in solution, we recommend the proteins tutorial.
  • This tutorial uses the graphical interface of AUSAXS (see Part 0 for installation instructions).
  • To easily visualize molecular structures, we will use PyMOL (see Part 0 for installation instructions).

Learning outcomes

After completing this tutorial you will:
  • Know how a SAXS curve is calculated from an atomic structure.
  • Know what rigid body modeling is, and when it is the right tool.
  • Be able to identify flexible linkers in a structure and refine the resulting rigid bodies against SAXS data.
  • Be able to understand and use structural symmetries in rigid body refinements.

Introductory remarks

Rigid body refinement is for the case where you trust the individual domains of a structure, e.g. from crystallography or AlphaFold, but not the way they are arranged relative to each other. This tutorial explores how they work, and how to use them in practice. We will work through four cases of increasing size, from a single fixed structure to a 36-body symmetric assembly.

Part 0: Installation

AUSAXS is installed with a single command. Open a command window (Terminal on macOS) and type: 

python -m pip install pyausaxs[all]

The [all] suffix pulls in the optional plotting and GUI dependencies. This installs a new command, ausaxs, which is the entry point for all the tools. Start the GUI by running the command: 

ausaxs gui

The window has three tabs across the top:

  • SAXS fitter — calculate the scattering from a fixed structure and fit it to data. This is Part I.
  • EM fitter — the same, for electron microscopy maps. See the Comparing with Electron Microscopy tutorial if you are interested.
  • Rigidbody — the refinement engine. This is Parts II–IV.

Later, we will use PyMOL to visualize the structures. While this is not strictly necessary, it is useful for inspecting the results.
PyMOL comes in two versions: as a free open-source program, and as a paid but more feature-rich program. Either can be used for this tutorial. To install the free version, run the command: 

python -m pip install pymol-open-source

This installs another command, pymol, which opens the PyMOL window. You can also download the paid version from pymol.org.

Part I: Does the structure already fit?

Before refining anything we need to ask a simpler question: how well does this structure already explain my data? Everything the refinement does later is just this calculation, repeated many times.

Only variations in density produce measurable scattering. What a SAXS curve reports is therefore not the absolute density of your sample, but how much it deviates from the surrounding buffer, and this is what a calculation from an atomic structure has to reproduce. This leads to three contributions:

  • The protein. Its density follows directly from the atoms in the structure file.
  • The excluded volume. A uniform buffer density, filling the entire region we model: the protein together with the hydration shell around it. Subtracting it converts the absolute density above into the excess density that is actually measured.
  • The hydration shell. Water packs more densely at the protein surface than in bulk. What survives the subtraction above is this extra density, and it has to be modeled since it is nowhere in the structure file.
The excess density of the sample: the molecule plus its hydration shell, minus a uniform buffer density filling the whole modeled region.

The three densities are combined first, and the scattering of the result calculated. In AUSAXS the Debye formula is evaluated over all pairs of scatterers to obtain the scattering, but the spherical harmonic expansion, as used in e.g. CRYSOL, is a popular alternative.

    Fit a SAXS dataset to a protein structure
  • Download the SAXS data for PA1 and the PA1 structure. PA1 is a monomeric pea albumin; the structure is an AlphaFold prediction with the signal peptide removed.
  • Open the SAXS fitter tab and load the two files (you can also try dragging them into the window, though this is somewhat unreliable on Linux).
  • Leave the settings at their defaults for now: hydration model radial, excluded volume model simple.
  • Press Run fit. The log pane reports progress, and when it finishes a set of result tabs appears next to it.
  • Look at the log and loglog tabs, and at the fit report. Note the value of $\chi^2_{red}$ and of the hydration contrast cw.
  • Run the fit a second time without changing anything. The $\chi^2_{red}$ will move slightly: the hydration layer is placed by a stochastic procedure, so repeated fits of the same structure differ a little. Take this as your noise floor: a difference of a percent or two between two models is not enough to judge which is best.

Evidently, the PA1 structure fits the data reasonably well. The $\chi^2_{red}$ is not too far from 1, the fit looks decent, and there are no obvious systematic deviations in the residuals. Given this relatively noisy data, the structure is therefore a good model for the solution conformation of PA1.

Finally, a case where the agreement is bad, and the whole point of the rest of the tutorial. Download LAR1-4.pdb and LAR1-4.dat, the first four domains of the flexible human leucocyte common antigen-related protein, and fit them as above. You should get $\chi^2_{red} \approx 50$. The domains are almost certainly right; their arrangement is not. Fixing that is a rigid body problem.

What the refinement does with this

A rigid body refinement treats a structure as a small number of rigid bodies connected by flexible linkers. The internal structure of each body is left untouched; only the relative positions and orientations of the bodies are optimized.

LAR1-4 split into 5 bodies connected by 4 flexible linkers.

The optimizer then proposes a new arrangement of those bodies, runs exactly the calculation you just ran in the SAXS fitter, and keeps the change if $\chi^2_{red}$ improved — a few thousand times over. Everything in the rest of this tutorial is about controlling those proposals: which bodies may move, how far, and what holds them together. Before we get to the LAR1-4 example, we will look at a simpler case: a dimer of the pea albumin PA2.

Part II: Symmetry, and the PA2 dimer

PA2 is a pea albumin that dimerizes in solution. We again have an AlphaFold model of the monomer, and SAXS data on the dimer. The task is to find how the two copies sit relative to each other.

The naive approach is to load two copies of the monomer and refine them as two independent bodies. AUSAXS instead lets you declare a symmetry: you load one copy, and state that the assembly has $p2$ symmetry. The second copy is then not a body at all: it is generated on demand from the first by a transformation whose parameters are what gets optimized. This matters for three reasons:

  • Fewer parameters. Two free bodies have 12 degrees of freedom, of which 6 are the global placement that SAXS cannot see, leaving 6 meaningful ones. A $p2$ symmetry has exactly those 6 (a translation and a rotation), and no redundant ones. The optimizer never wastes a step on a global move.
  • The symmetry is enforced. For more complex systems, two independently refined copies may drift into an asymmetric arrangement, because nothing stops them. A declared symmetry is exact by construction.
  • It is cheaper to evaluate. Declaring a symmetry switches AUSAXS to a symmetry-aware distance calculator, which computes one representative distance histogram per symmetry-equivalent pair of copies instead of all of them. We return to this in Part IV, where it matters a great deal.

The symmetry groups available in AUSAXS are:

NameCopies generatedDescription
p21A single freely-oriented copy. The natural choice for a dimer.
c2–c121–11Cyclic: copies are generated by repeated rotation about a common axis.
d2–d123–23Dihedral: a cyclic axis plus perpendicular 2-fold axes.
dp2–dp123–23Planar dihedral, where all copies are coplanar.
tetrahedral, octahedral, icosahedral11, 23, 59The chiral polyhedral rotation groups.

These can also be composed: p2-p2 is a dimer of dimers, in which the inner and outer relations are optimized independently. This is the looser cousin of d2, which we will meet in Part IV.

    Refine the PA2 dimer
  • Download the PA2 SAXS data and the PA2 monomer structure.
  • Open the Rigidbody tab and open both files. The script in the middle panel updates its load block to match.
  • Click the "View" button next to the Structure field to open the structure pane. This is where all setup work is done.
    Expand the Symmetry section, type p2 into the Add symmetry to a body field, and press Apply.
    The generated copy appears in the preview immediately, and symmetry p2 is listed under Applied elements.
  • Press Send to script…, review the change, and confirm. You are now back at the script, with the symmetry declaration inserted.
  • Edit the parameter block to read: 
    parameter {
	iterations 500
	sym_translate 20
	sym_rotate 1.5
}
  • Press Validate to check the script parses, then Run refinement. The structure preview updates live as better conformations are found.
  • When it finishes, compare the initial and final $\chi^2$. You should see a drop from roughly 1300 to below 5 — and most of that happens within the first few tens of iterations, as you can see in the log.

Two things in that script are worth dwelling on.

Why only sym_ amplitudes? The parameter element sets the maximum size of the moves attempted each iteration, and it has four independent components: translate and rotate move the bodies themselves, while sym_translate and sym_rotate move the symmetry parameters. Here the symmetric partner is generated from the base body's current position, so translating or rotating the base body moves the whole dimer rigidly and changes nothing about the scattering (except for minor differences due to the stochastic hydration shell). Setting those to zero by simply not naming them means the optimizer spends every step on something that can actually help.

Units. translate and sym_translate are in Ångström; rotate and sym_rotate are in radians. A sym_rotate of 1.5 is a large move — nearly 90° — which is what you want at the start of a search. The amplitudes decay over the course of the run (exponentially by default, see the decay argument), so the run begins with a coarse global search and finishes with fine adjustments.

Exercises
  • Look through the script and locate the output folder on your disk. What files are present, and why?
    Open the initial_state.pdb and final_state.pdb files in PyMOL and compare the two. What is different?
    Finally, open the trajectory.xyz file in PyMOL. This is a multi-frame coordinate file, and PyMOL will animate it if you click the "start" button in the bottom-right corner. How does the dimer move during the refinement?
  • Look at the rest of the script. What is the purpose of the loop and optimize_once elements? Where is the loop counter?
  • Validate that using real-space transformations (translate, rotate) does not change the structure of the dimer.
    To do this, you will need to move the update structure outside the on_improvement block (but still inside the optimize_once block — why?), so that the structure preview is updated every iteration.
  • Repeat the fit, but using the dimer generated by AlphaFold. Since this is already a dimer, you should no longer declare this symmetry. Instead, you can decompose it into one, via the Decompose bodies into a symmetry field in the structure pane.

Part III: Flexible linkers: the LAR1-4 structure

We return to the LAR structure from Part I. This is a flexible multi-domain protein: the individual domains are well determined, but the crystal conformation is not the solution conformation. Here there is no symmetry to exploit, and the work is instead in deciding where the structure is allowed to bend.

    Split a structure into rigid bodies
  • In the Rigidbody tab, load LAR1-4.pdb and LAR1-4.dat.
  • Start by checking how well it fits the data by using the SAXS fitter. You can do this quickly by clicking the Send to SAXS fitter button.
  • Open the structure pane. You get a rotatable Cα trace. Rotate it until you can see the domain organisation: the compact globular regions are the rigid bodies, the extended stretches between them are the linkers.
  • Hover over the trace — the readout above the plot names the residue under the cursor. Click on each linker you have identified; the residue is marked with a coloured sphere.
  • With your residues selected, press Apply next to Split at residues. The structure is re-partitioned and each body is drawn in its own colour. Check in the Bodies list that you got the number of bodies you expected.
  • Bodies that are not tied together will fly apart, since nothing in the SAXS data holds a broken backbone together. Expand Constraints, and with backbone already filled in, press Generate. This finds the Cα atoms at the body endpoints and links each neighbouring pair. The connected bodies will be joined by a dashed line in the preview.
  • Press Send to script… and confirm.

Your script should now look roughly like this. Set the parameter block, and add the select and transform lines:

output output/rigidbody/
load {
	pdb LAR.pdb
	saxs LAR.dat
	split 7 99 199 292
}
autoconstrain backbone

save initial_state.pdb
save trajectory.xyz
parameter {
	iterations 200
	translate 1
	rotate 0.2
}
select random_constraint
transform rigid_transform

print "Initial chi2: {chi2_no_penalty}"
loop
	optimize_once
		on_improvement
			print {
				msg "{iteration}/{iterations_total}: Accepted with new chi2 {chi2_no_penalty}"
				colour green
			}
			update structure
			save trajectory.xyz
		end
	end
end
save final_state.pdb
The three elements that control how a step is taken are:
  • parameter: how large a move to generate.
  • select: which body to move via a constraint, since AUSAXS uses the constraints themselves as pivots for moves. The default option is random_body which first selects a random body, then a random constraint attached to it. Here, we instead use random_constraint, which just selects a constraint randomly, without selecting a body first. The difference is subtle but important: if a body has many constraints, random_constraint will pick it more often than a body with few, while random_body would bias the sampling towards bodies with few constraints. The other options are sequential_body and sequential_constraint, which cycle through the bodies or constraints in order, and finally you can also name a specific body (or symmetry) to move.
  • transform: how the move propagates. rigid_transform carries everything connected to the selected body along with it, so the chain stays intact; single_transform moves only the selected body, which will strain its constraints unless the amplitudes are small.

Note also update inside the loop: this is what feeds the live preview. And the article this data comes from discards points below $q = 0.0125$ Å$^{-1}$ because of aggregation — do that with the $q$-slider in the dataset tab before running.

    Run it
  • Press Run refinement. At least 500 iterations are needed for convergence; watch the preview and the accepted-$\chi^2$ messages in the log.
  • The authors of the paper ran the optimization 10 times and found $\chi^2$ between 3.7 and 4.3. Does your result land in that range? A single 500-iteration run will typically get you to around 5, so if you want to match the paper you may need more iterations or several runs.
  • They also report that the final structure is "L"-shaped. Open initial_state.pdb and final_state.pdb in PyMOL and compare. Is yours?
Exercises
  • During the 500-iteration run, you may have encountered a few steps where $\chi^2$ increased. Why would the optimizer accept a worse conformation?
    To examine this, look at the print element and what options it has for formatting the message. Change the message to something more informative, e.g. "{iteration}/{iterations_total}: {chi2} ({chi2_no_penalty} + {chi2_penalty})", and re-run the optimization.
  • You just saw how the $\chi^2$ is composed of a "no penalty" term and a "penalty" term. What is the penalty, and why is it needed?
    To see the effect of the autogenerated backbone constraints, try running the optimization with autoconstrain none instead.
  • To completely remove the penalty term, you can also add the undocumented overlap_strength 0 element to the script. The overlap (excluded volume) penalty is what keeps the bodies from moving through each other, and setting its strength to zero removes that. What happens to the printed $\chi^2$ values and the structure? Note: this element is only for demonstration purposes, and should not be used in a real refinement.

Part IV: A large symmetric assembly — A2M

α-2-macroglobulin (A2M) is a protease inhibitor that circulates as a homotetramer with $D_2$ symmetry: four identical chains of ~1440 residues, related by three mutually perpendicular 2-fold axes. Each chain is a chain of domains joined by flexible linkers, so this problem has both of the features we have handled separately — symmetry, and internal flexibility — at a scale where doing it naively is genuinely expensive.

Consider what "naively" would mean. Eight linkers per chain gives nine bodies per chain, so 36 bodies in total, and 36 × 6 = 216 degrees of freedom. Nothing would keep the four chains identical, so the refinement would be free to produce a tetramer that is not a tetramer. And the scattering calculation would need a partial distance histogram for every pair of bodies: 36 × 37 / 2 = 666 of them, recomputed every accepted step.

Declaring the $D_2$ symmetry instead: nine bodies of one chain, 54 degrees of freedom, plus 6 parameters describing the symmetry itself — a factor of four fewer, with the tetramer exact by construction. The scattering calculation shrinks too. For a single body under $D_2$ there are four copies, and so ten pairs; but the distance distribution between copies $i$ and $j$ depends only on the group element relating them, and the four-element $D_2$ group has only three distinct non-identity elements. So four distinct histograms are evaluated instead of ten, each scaled by its multiplicity. The same reuse applies to every pair of bodies.

Step 1: load and decompose
  • Load A2M_native.pdb and A2M_native.dat into the Rigidbody tab.
  • The file contains all four chains, A–D. In the structure pane, type chain into Split at residues and press Apply to load them as four separate bodies. The Bodies list should show b1 through b4.
  • Expand Symmetry and use the second row, Decompose bodies into a symmetry: enter b1 b2 b3 b4 d2 and press Convert.
  • Three of the four bodies disappear from the list. What is left is b1 plus a fitted $D_2$ symmetry that regenerates the other three, shown in the preview as b1s1r1, b1s1r2 and b1s1r3. The log reports the residual RMSD of the fit — for this structure it is essentially zero, because A2M really is exactly $D_2$.

That last number is a check, not a formality. convert_to_symmetry asserts a symmetry you have claimed, fits its parameters to the copies you gave it, and refuses the conversion if the residual exceeds a tolerance (5 Å by default, adjustable in the advanced field). If you try c4 here it will fail, and that failure is informative: the four chains are not related by a single rotation axis.

If your own assembly is only approximately symmetric, the looser composite p2-p2 is worth trying — it is a dimer of dimers with the inner and outer relations optimized independently, so 12 parameters rather than 6.

Step 2: split into domains
  • You now want to split b1 at its linkers — but not with the Split at residues field, which re-reads the file and would undo the decomposition. Click the chevron (▸) beside it to reveal Additional splits (an existing body). This row emits a split element, which partitions a body already in the setup and ties the fragments into the symmetry it already carries.
  • Find the linkers as in Part III: rotate the preview, hover to read residue numbers, click at each domain boundary. With the symmetry copies displayed this is cluttered — turn off Symmetry copies under Display while you work.
  • With the residues selected, type b1 in the field and press Add.
  • Expand Constraints and press Generate with backbone to link the fragments.
  • Send to script… and confirm.

A2M has eight reasonably clear domain boundaries per chain. If you want a reference set, the residues below work — they were located by looking for points where the chain moves between spatially separate lobes: 

split b1 123 225 347 453 616 697 907 1330

Residue 697 sits in the bait region, the exposed loop that proteases cleave to trigger A2M's conformational change — a genuinely flexible part of the molecule rather than an artefact of the heuristic.

Step 3: refine

Your script should now be close to:

output output/rigidbody/a2m
load {
	pdb A2M_native.pdb
	saxs A2M_native.dat
	split chain
}
convert_to_symmetry d2
split b1 123 225 347 453 616 697 907 1330
autoconstrain backbone

save initial_state.pdb
parameter {
	iterations 2000
	translate 0.5
	rotate 0.02
	sym_translate 2
	sym_rotate 0.03
}
select random_constraint
transform rigid_transform

print "Initial chi2: {chi2_no_penalty}"
loop
	optimize_once
		on_improvement
			print "{iteration}/{iterations_total}: chi2 {chi2_no_penalty}"
			update structure
			save trajectory.xyz
		end
	end
end
save final_state.pdb

All four amplitude components are in play here, and their relative sizes encode a modeling decision: the domains are nudged (translate, rotate), while the overall $D_2$ arrangement — the thing most likely to differ between crystal and solution — is given a little more room (sym_translate, sym_rotate). Setting translate and rotate to 0 refines only the tetramer geometry with each chain held rigid, which is a perfectly reasonable first experiment and much faster.

Note how small all four are compared to Parts II and III. The A2M crystal structure already fits at $\chi^2_{red} \approx 8.5$, so we are polishing rather than searching, and large moves are simply rejected. Amplitudes decay over the run, so an over-large starting amplitude does not break the refinement — it just wastes the early iterations until the decay brings the moves down to a size that gets accepted. With the values above the first improvements arrive within the first tens of iterations; with amplitudes a few times larger, nothing is accepted for the first hundred. Expect a modest improvement here, not the dramatic drop you saw for PA2: this structure is close to right already, and the exercise is the setup.

    Run and compare
  • Run the refinement. This is a large structure, so expect it to take considerably longer per iteration than the earlier parts.
  • Run it again with translate 0 and rotate 0, refining only the symmetry. How much of the improvement came from the tetramer geometry alone, and how much needed the domains to move?
  • Try refining without the symmetry at all: delete the convert_to_symmetry line, split each of b1–b4 separately, and compare both the wall-clock time per iteration and whether the result still looks like a tetramer.

Challenge: staged refinement

Everything so far has used a single flat loop, which is not what the script language is for. It is a real language rather than a configuration format: loops nest to any depth, and parameter, select and transform are ordinary elements that take effect where they appear. You can therefore change the refinement strategy during a run, as often as you like.

A2M is a good case for this. We have been moving the domains and the $D_2$ symmetry in the same step, which means a proposal is accepted only if both happen to be improvements — so most proposals are rejected for the wrong reason. Refining them in alternating phases is the better strategy: settle the domains for a while with the tetramer held fixed, then settle the tetramer with the domains held fixed, and repeat.

The construction is a nested loop, where the inner block is given a name and then re-run under different parameters: 

loop 100
	# phase 1: move the domains, tetramer geometry held fixed
	parameter {
		iterations 2000
		translate 0.5
		rotate 0.02
	}
	loop refine 20
		optimize_once
			on_improvement
				print "{iteration}/{iterations_total}: chi2 {chi2_no_penalty}"
				update structure
				save trajectory.xyz
			end
		end
	end

	# phase 2: the same block again, now moving only the tetramer
	parameter {
		iterations 2000
		sym_translate 2
		sym_rotate 0.03
	}
	loop copy refine
end

loop refine 20 names the loop; loop copy refine runs that same block a second time. Note that the copy takes no end — it does not open a scope of its own. This matters more than it might look: the inner block is where all your reporting lives, and it can grow as elaborate as you like (nested every blocks, saves, conditional prints) without ever being duplicated. Write it once, re-run it under as many parameter sets as you want.

One detail to get right: iterations in each parameter block is the decay timescale of that generator, not the length of the run. The two phases keep independent decay schedules, so each should be set to the number of steps that generator will actually be used for — here $100 \times 20 = 2000$ each.

    Build a staged refinement
  • Run the two-phase script above and compare its $\chi^2$ against the flat version from earlier, at equal total step count. Does separating the phases help?
  • Add a third phase that refines one domain at a time. The select element accepts a body name, not just a strategy — select b5 restricts the following steps to that body, and this is exactly what naming individual bodies is for. A loop over each body in turn is a very different search from picking one at random.
  • Make the phases uneven. Early on, the tetramer geometry is what matters most; near the end, the domains. Try giving phase 2 more iterations at the start and fewer later, by using two differently-sized outer loops in sequence.
  • Use every inside the inner block to report progress on a schedule of your choosing, rather than only on improvement — useful when a phase is rejecting everything and you want to know it is still alive.

Perspectives

The script in the middle panel is the whole interface — the GUI only ever writes into it, and you can save it with the disk icon and re-run it later with ausaxs rigidbody myscript.conf, on a cluster or in a loop over many datasets. The full set of elements is documented on the AUSAXS wiki.
